# Workspace knowledge page access

Workspace pages remain shared with all active Ashbi staff by default. A creator can choose restricted access before the first save, so private content is never briefly published to the team. Restricted pages allow selected active staff to read or edit content. Organization administrators retain access. The original page author is the owner; owner management also depends on ancestor access. Clients and foreign organizations are denied.

Every ancestor must permit reading a descendant. Read-only access to any ancestor also makes descendants read only. A child grant cannot open a restricted parent. Search, page lists, nested-page navigation, parent choices, single-page reads and MCP reads use the same authorization. Lists scan cursor-ordered candidates in batches of 100 until an authorized page is filled; returned cursors identify visible records, not hidden rows. The request-local ancestor cache is cleared between batches and never loads content or other users' grant rosters.

Content editors cannot move, archive, restore or change page audiences. Owners and administrators manage those boundaries. Moving a page changes its inherited access and requires edit access to the destination parent. Archiving a restricted parent with active children is refused, including at the database boundary: move or archive nested pages first. This prevents automatic child promotion from widening a private subtree's audience. Archiving shared parents retains the existing promotion behaviour. Historical archived descendants remain subject to ancestor permissions.

Owner/admin access settings use their observed access revision, unique staff grants (up to 100), and serializable compare-and-set updates with a required audit record. New or changed grants require current active staff; unchanged inactive grants can remain visible for review and removal but confer no access. The page owner is implicit and cannot be duplicated in the roster. Database guards enforce grant organization/page/user identity, block reverse grantee transfers and make original authorship immutable. Raw grant edits advance both access and document revisions, so stale content drafts and access drafts cannot silently overwrite them.

GET/PUT /api/wiki/pages/:id/access exposes the owner-controlled roster. GET /api/wiki/pages/:id/access/options provides bounded, searchable staff choices with cursor pagination. These do not use a truncated global team list. UI errors preserve the original draft revision; failed reloads retain the draft. Read-only viewers do not receive edit, hierarchy, archive or audience controls.

MCP get_workspace_page_access uses the same management check. set_workspace_page_access prepares exact before/after rosters with names and an explicit descendant-visibility notice; confirmation rechecks the requester's current identity, authority and access revision. Existing content actions recheck inherited permissions at confirmation, so revoked previews cannot execute. All mutations, grants, required audit and confirmed action receipts share one transaction. Governance, idempotency, scope, expiry and input limits stay in force. Denied wiki tool reads/previews use typed errors so the governed executor records denial evidence.

Organization-owner exports include current grants alongside canonical pages, hierarchy, authors and archived content. This is not a staff-readable export of restricted pages. No live access, production security settings, release gates or source data changed during implementation.

This access model applies to workspace wiki pages. Project Note audiences (#592), retained content history (#606) and explicit manual conflict reconciliation are implemented separately; these access grants do not themselves implement history storage or change its authority. The approved history policy retains the newest **100 revisions including current**, allows authorized historical reads and **ADMIN restore as a new edit**, with **no automatic time purge**. See [document recovery policy](document-recovery-decision.md), [Project Note audiences](project-note-audiences.md) and [manual conflict recovery](document-conflict-recovery.md). Real-time collaborative convergence and populated team acceptance remain open; synthetic concurrent-edit recovery is distinct from convergence. The [dated launch record](launch-status.md) retains scoped verification evidence, and [#565](https://github.com/camster91/ashbi-platform/issues/565) owns the current execution queue.

Acceptance requires raw and request-scoped PostgreSQL grant boundaries, inherited read/edit denial, client/foreign/inactive identities, stale administrator claims, archive protection, hidden-record pagination, competing access writes, revoked action previews and exact confirmed receipts/audit. Browser acceptance must prove restricted creation, persisted audience changes, conflict draft recovery and mobile accessibility/reflow. CI, independent review and target/team acceptance are distinct gates.
