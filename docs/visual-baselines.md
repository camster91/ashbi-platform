# Visual-regression baselines

Issue [#322](https://github.com/camster91/ashbi-platform/issues/322). Committed
screenshots of representative screens, compared pixel by pixel on every run so
token, component and layout changes cannot shift a screen unnoticed.

**Status: proposed baselines, opt-in.** The PNGs in
`tests/visual/__screenshots__/` were generated by engineering and still need the
design owner's approval (see [Ownership](#ownership-and-approval)). The suite is
not a required release gate yet (see [CI](#ci)).

## What is covered

|---|---|---|---|---|---|---|
| Login | `/login` | yes | yes | yes | yes | |
| Shell + Dashboard | `/dashboard` | yes | yes | yes | yes | light 768; shows the one-time push-notification prompt |
| Clients list | `/clients` | yes | yes | yes | yes | |
| Projects list (kanban) | `/projects` | yes | yes | yes | yes | |
| Project page | `/project/project-a` | yes | yes | yes | yes | |
| Invoices list | `/invoices` | yes | yes | yes | yes | |
| Daily Queue | `/queue` | yes | yes | yes | yes | |
| Settings | `/settings` | yes | yes | yes | yes | |
| Client portal home | `/client-portal` | yes | yes | n/a | n/a | the portal is light-only (`usePortalLightTheme`) |
| UI lab gallery | `/ui-lab` | yes | yes | yes | yes | full-page: alerts, empty state, skeletons |

39 screenshots in total, about 3.4 MB. Staff screens are captured at the
viewport (375x812, 768x1024, 1440x900) because the shell scrolls inside its own
main region; the UI lab is captured full-page.

Not covered yet (the rest of the #322 matrix): Firefox and WebKit, the other
widths (320/430/1024/1366/1920), 200%/400% reflow, forced colours, focus,
loading/error/offline states per screen, dialogs, public finance links and
email rendering. Add them here as they are approved; keep the suite small
enough to review (roughly 40-60 images).

## How it works

- Config: `playwright.visual.config.ts`. Chromium only, one project named
  `chromium`, `deviceScaleFactor: 1`, locale `en-US`, timezone
  `America/Toronto`, `reducedMotion: 'reduce'`, and `animations: 'disabled'`
  and `caret: 'hide'` on every screenshot.
- It builds the SPA with `VITE_ENABLE_UI_LAB=true` into `web/dist-visual`
  (gitignored; the production `web/dist` is not touched) and serves it with
  `vite preview` on port 4189 (`PLAYWRIGHT_VISUAL_PORT` overrides). The flag
  only adds the dev-only `/ui-lab` route; production builds never set it.
- Specs: `tests/visual/screens.spec.ts`, helpers in
  `tests/visual/visual-helpers.ts`.
- Data: the hermetic fixtures in `tests/fixtures/authenticated-api.ts` (the
  same ones the accessibility smoke uses), plus a Daily Queue fixture in the
  helpers. Every record is invented (`Northwind Studio`, `example.com` and
  `.example` addresses); no production or personal data. Any `/api` request
  without a fixture fails the test, so fixture drift cannot silently produce a
  half-empty screenshot.
- Time: `page.clock.setFixedTime('2026-08-20T15:00:00Z')`, the fixtures' "now".
  Dates, greetings and relative times ("1d ago") render the same on every run.
  Timers are not faked, so data fetching behaves normally.
- Fonts: the app declares its self-hosted fonts with `font-display: optional`,
  which makes a cold page fall back to the system font on some runs. The suite
  serves the stylesheet with `font-display: block` and waits for every face to
  load, so baselines always show DM Sans and Instrument Serif.
- Realtime: socket.io is blocked (there is no backend), and the
  push-notification prompt is marked as already answered on every screen except
  the dashboard.

## Running

```bash
npm run test:visual
```

Playwright's bundled Chromium is used by default. In a sandbox that ships its
own Chromium, point at it with `PLAYWRIGHT_CHROMIUM_EXECUTABLE_PATH`; the
baselines are only comparable against the Chromium build they were made with.

Failures write `*-actual.png`, `*-expected.png` and `*-diff.png` plus a trace to
`test-results/visual/`. Open the trace with `npx playwright show-trace <zip>`.
In CI the HTML report is written to `playwright-report/visual/`.

## Updating baselines

Only update after a deliberate visual change, never to make a flaky run pass.

1. Make the change and run `npm run test:visual` to see which screens moved.
2. Regenerate: `npm run test:visual:update` (the same as
   `npm run test:visual -- --update-snapshots`). To limit it to one screen:
   `npm run test:visual -- --update-snapshots -g "queue"`.
3. Review every changed PNG before committing: `git diff --stat
   tests/visual/__screenshots__`, then compare old and new images in the pull
   request's rich diff (GitHub's swipe/onion-skin view) or locally.
4. Run `npm run test:visual` twice more without `--update-snapshots`; both must
   pass.
5. Commit the PNGs in the same pull request as the change, and ask the design
   owner to approve them.

Baselines are platform-suffixed (`<screen>-<theme>-<width>-chromium-linux.png`)
so a macOS or Windows render is never compared against a Linux one. Generate
and update them on Linux (Ubuntu 24.04, as used by `ubuntu-latest`).

The committed set was generated in a Linux container with Chromium
141.0.7390.37 (a pre-installed build), while `npx playwright install` on
`ubuntu-latest` currently installs Chromium 153 for `@playwright/test` 1.63. A
different Chromium build can render text anti-aliasing and some raster details
differently. **Before turning this into a gate, regenerate the baselines once on
the CI runner** (for example, a manual workflow run of
`npm run test:visual:update` that uploads `tests/visual/__screenshots__` as an
artifact), review them, and commit that set. Upgrading Playwright or Chromium
later is also a deliberate baseline update.

## Thresholds

Set in `playwright.visual.config.ts` under `expect.toHaveScreenshot`:

- `threshold: 0.2`: per-pixel colour distance (YIQ, 0-1) below which two
  pixels count as equal. Playwright's default; absorbs anti-aliasing.
- `maxDiffPixelRatio: 0.01`: at most 1% of the image may differ. A real
  layout, spacing, colour-token or font change moves much more than that in a
  viewport capture; one changed word may not, so review diffs, not just
  pass/fail.

Do not raise either to make a test pass; mask the region or fix the
nondeterminism instead.

## Masking rules

`volatileRegions()` in `tests/visual/visual-helpers.ts` paints a solid box over:

- running timers and anything that reads the live clock: `[role="timer"]`, and
  any element marked `data-visual-mask`;
- relative times rendered in `<time>` elements;
- avatars and other images loaded from remote (non-same-origin) `http(s)` URLs.

Prefer fixing nondeterminism in the fixture (a fixed date, a same-origin
image) over masking. If a new screen needs a mask, add `data-visual-mask` to
the element in the app or extend `volatileRegions()`, and say why in the
pull request. Never mask a whole panel.

## Ownership and approval

- **Design owner**: approves baselines. A pull request that adds or changes a
  PNG under `tests/visual/__screenshots__/` needs their review of the images,
  not only the code.
- **Engineering**: keeps the suite deterministic and fixtures realistic, and
  investigates any failure that is not an intended change.
- Fixtures must never contain production or personal data; follow the
  sanitization rules in [#322](https://github.com/camster91/ashbi-platform/issues/322).

## CI

The suite is **opt-in** and not part of the required release gates in
[release-gates.md](release-gates.md). The baselines were made on a different
Chromium build than CI installs, so a gating run would fail on rendering noise
rather than real regressions. To promote it:

1. Regenerate and approve the baselines on `ubuntu-latest` (see above).
2. Run it there repeatedly (for example `--repeat-each=3`) and confirm it is
   stable.
3. Add `npm run test:visual` to the browser job in
   `.github/workflows/release-gates.yml` and update
   `npm run check:release-gates` and `docs/release-gates.md` together.

Known issue captured by the proposed baselines: at 375 px the UI lab's
skeleton headers are wider than the viewport, so that full-page capture is 568
px wide. The shared `PageSkeleton` headers overflow on narrow screens.
