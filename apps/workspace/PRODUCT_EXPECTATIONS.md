## Implemented slice: reusable task views

The Tasks page now offers Assigned to me for staff and explicit named saved views for each account/project context. A view stores applied search/project/status/assignee filters, archived-project inclusion and List/Board layout. Apply always re-queries the existing API; it does not cache results or widen authorization. Project routes retain their project boundary. Clear filters leaves saved views intact. Removing a view removes preferences only.

Preferences stay on the current browser/origin, keyed by actor ID and project ID; they are not team-shared or synchronized. They may contain the user's view names/search text and opaque record IDs. Saving is explicit and explained before storage. Limits are 20 views per context, 60-character names and bounded validated preference records. Duplicate names, unavailable/full storage and malformed stored data produce visible errors. No credentials or task bodies are stored. Browser data clearing removes the views.

## Controlled client uploads

Staff can now enable **Allow client uploads** when adding or editing a project. Migration `0029.sql` adds a default-off flag. Clients can upload only to their own shared, non-archived projects with this setting enabled. Client uploads are shared with the team and authorized contacts for that client; deletion, restoration and sharing changes remain staff controls.

Active identity, organization, role, client ownership, sharing, archive status and opt-in are checked before upload and atomically before publication after storage. A revoked upload remains pending and unavailable. The 5 MiB stream limit, safe filenames, private originals, checksum verification, attachment-only downloads and Origin checks remain enforced. Disabling uploads prevents new submissions without unsharing existing files.

## Project conversations

Each project now has a Messages tab for staff and authorized client contacts. Messages are plain text, newest first, with explicit refresh and older-history pagination. Project sharing controls client visibility; archiving makes the conversation read-only. Message history is retained without edit/delete controls. No email, push notification or real-time subscription is implied.

The API validates active actor identity and project scope in reads and atomic inserts. Author IDs are server-owned. Per-author request IDs recover repeated/concurrent submissions once; reusing an ID with different content or another project conflicts. The interface retains the draft and original request ID for uncertain replies in the current page session, prevents editing an uncertain submission, and ignores stale view responses. ## Personal unread inbox

Inbox lists unread messages from other people in projects the current account can access. Opening a conversation does not silently mark it read. Each inbox item has an explicit Mark message read action; the Messages tab shows Unread badges and Mark loaded messages read. Read state is private to the signed-in account and persists in D1 across sessions/devices. Your own posts never create unread notifications for you.

The sidebar count refreshes on navigation, focus, visibility changes and every 30 seconds while visible. Inbox rows and conversation history have explicit refresh controls; this is polling, not real-time push. Counts above 99 display 99+ with the exact count in the accessible name. A failed count request hides the stale badge and identifies the count as unavailable. No notification previews are persisted in browser storage.

Migration `0031.sql` adds per-account, per-message read receipts. Exact message IDs keep arrivals during a read action unread; repeated requests are safe after a lost acknowledgement. Current organization, active identity and client project permissions are enforced during both reads and atomic receipt insertion. Inaccessible/nonexistent IDs receive the same response. Archived project history can still be marked read. Read receipts are included in full recovery backups, not the general staff record export.

## Expanded Inbox: implementation after PR #788

The Inbox now combines project messages, task assignments, due/overdue tasks and newly published client uploads. Staff receive assignment and deadline notifications for their own tasks and upload notifications for their organization. Clients receive only messages from currently shared projects belonging to their client account. Current actor activity, role, organization and resource permissions are checked again for each read and receipt mutation.

Assignments receive a new durable token on creation with an assignee and on an actual assignee change. Title/status edits do not invent new assignment alerts. Reassignment creates a fresh token in the same task write. Assignment/deadline alerts leave the Inbox when the task is completed, retired or archived, the project is archived, or the task is no longer assigned to that account. Due-date reminders become available on the due date (UTC); their ID includes the task and due date. These are in-app reminders, not scheduled email or push delivery. Existing assignments are not backfilled as new assignment events; existing due/overdue assigned tasks are eligible.

Client-upload alerts appear only after successful publication, never while storage is pending, and disappear when the file is deleted. Existing files are not backfilled. Following a file notification opens that project's Files section; task notifications open the task. Project-message notifications retain the existing per-account receipts.

Unread, Read and All filters provide a personal notification history within current permissions and actionable resource state. Mark read and Mark unread are idempotent explicit operations, scoped to exact typed IDs. The list is bounded to 50 rows with stable timestamp/type/ID pagination. Preference toggles persist per account in D1, apply consistently to rows and counts, and never change receipt state. Muting and re-enabling a category restores its prior read/unread state. Client preferences show only the category available to clients.

Additive migration `0032.sql` adds assignment metadata, upload publication flags, personal preferences and typed read receipts, plus indexes for assignment and upload queries. Previous Worker code remains compatible with the additive schema. Full database backups include private preferences/receipts; general staff exports do not. Deploy only after backup, migration rehearsal and verified artifact promotion. This increment is local until separately recorded as released.

Remaining readiness work includes email/push delivery, provider-backed billing acceptance, a scoped security assessment, representative production performance measurements and signed-in owner acceptance. These are not established by the notification tests.

## Structured project mentions

The message composer now provides **Mention people** with explicit checkboxes, up to 10 recipients, and a clear-selection control. Mentions are selected rather than inferred from arbitrary `@` text. Staff can select other active staff and active contacts for the project's client when the project is shared. Clients can select active staff only; they cannot enumerate other client contacts. The bounded recipient directory returns at most 100 eligible identities with email labels and role, only after verifying the sender's current project access. Long labels wrap on mobile. Recipient addresses stay in the current page; stored messages contain actor IDs rather than copies of those addresses.

Migration `0033.sql` adds the recipient-ID array to each message and a separate Mentions preference, enabled by default. All recipients are revalidated in the same statement that publishes the message. An invalid or revoked recipient rejects the whole new submission. The normalized recipient list is part of the retry identity: retrying identical recipients does not duplicate a message; changing recipients with an existing request ID conflicts. A previously accepted submission can still be recovered if a recipient subsequently loses access. The browser freezes both content and recipients during uncertain retries, retains selection with the current-page draft, and clears selection after confirmed success.

A mentioned message has a personal **You were mentioned** marker in its conversation and Inbox. It remains one notification with the existing message read receipt, not a second unread event. Mentions and ordinary project messages are distinct preference categories: ordinary messages can be muted while mentions stay enabled. Older four-category preference clients preserve the current Mentions setting when saving. Mentions never grant project access and never send email/push. Current project visibility and actor permissions continue to govern Inbox reads and receipt writes.
