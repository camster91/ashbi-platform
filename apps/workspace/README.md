# Ashbi workspace — private Cloudflare pilot

This is the deployable successor to the isolated local foundation proof. It uses verified Cloudflare Access JWTs and active D1 actors; there is no fixture-code login endpoint. It does not replace the current application or migrate production records.

## Local checks

Build is a dry-run only. `auth.test.mjs` verifies real RSA signatures and claims; `test.mjs` runs the application handler with real local D1 through Miniflare. ## Reviewed invoice drafts and source claims (source increment)

The invoice API prepares a reviewable draft from approved, completed, unclaimed billable time and fixed charges. ## Editable proposals, contract templates and contract preparation (source API)

`/api/commercial` stores private staff preparation on D1. All routes require a currently active staff actor with an explicit financial grant, including templates because they can contain fees and payment terms. Clients and ordinary staff cannot read drafts, histories, request receipts or their financial exports. No draft is shared through the portal. Existing proposal, contract, PDF, signature and delivery systems remain operational until their replacements pass acceptance.

- `POST /api/commercial/proposals`: UUID `requestId`, `title`, `clientId`, optional `projectId`, and `content`. Proposal content requires `scope`, `schedule`, `terms`, explicit `currency` (CAD/USD/EUR/GBP), `charges: [{description, quantity, unitMinor}]`, `discountMinor`, and `tax: {type, rateBps}`. An optional `depositMinor` requests part of the full total; it does not record a payment or start recurring billing. Schedule and terms may be empty for an unfinished draft. One to fifty charges use whole quantities and safe integer minor units. The server computes line totals, subtotal, discount, taxable amount, aggregate tax rounded half up, total and remaining balance using BigInt. Unknown/derived totals, fractional values, overflow and impossible discounts/deposits are rejected. Proposals do not claim time or issue invoices.
- `POST /api/commercial/templates`: UUID `requestId`, `title`, and `content: {text}`. Text is literal, bounded to 20,000 characters; it is not evaluated as HTML or a substitution program. No default legal terms are inserted or approved by the application.
- `POST /api/commercial/contracts`: UUID `requestId`, `title`, `clientId`, optional `projectId`, and explicit draft `content: {text}`. Optional `template: {id, revision}` and `proposal: {id, revision}` retain immutable source references and hashes. The selected sources must be current active drafts in the same organization; proposal client and project must align. Contract text is explicitly prepared by staff, not silently substituted or signed. Later edits to a template or proposal cannot rewrite an existing contract draft or its provenance. Source versions remain available in history.
- `GET /api/commercial/{proposals|templates|contracts}`: compact summaries, stable ID pagination with `after`, optional DRAFT/ARCHIVED `status`, and client/project filters for proposals and contracts. Fifty rows per page. `GET /:id` returns the full draft. Templates have no client/project association.
- `PATCH /:id`: UUID `requestId`, observed `revision`, and complete `title`/`content`. Replaces only an active draft's editable content; identity, type, client/project and provenance cannot be changed. Concurrent editors cannot overwrite one another silently. Historical client/project names and content remain in every prior snapshot; a new edit captures current names, rechecked atomically against the observed target records.
- `POST /:id/archive` and `/reopen`: UUID `requestId`, observed `revision`, required `reason`. Archive retains content and all history; reopen explicitly returns to preparation. There is no deletion endpoint.
- `GET /:id/history`: descending immutable versions, fifty per page, numeric `before` cursor. `GET /:id/history/:revision` returns the exact historical content, actor, time, action and reason.
- `GET /api/commercial/requests/:uuid`: UNKNOWN or SAVED with the exact mutation snapshot and `currentRevision`. Every mutation key is organization scoped across record types, so another authorized reviewer can recover a lost acknowledgement. Identical retries return the original saved revision even after subsequent edits. A different path or intent with that key conflicts. UNKNOWN does not prove an in-flight request failed; keep the same key and reconcile before re-entry.

Additive migration `0011.sql` creates `commercial_drafts` and `commercial_versions`. Each create/edit/archive/reopen commits its active financial authority, target/source checks, current draft and version in one [D1 batch](https://developers.cloudflare.com/d1/worker-api/d1-database/#batch). A final database constraint fence rolls back a writer whose version insertion was absent, including a no-op. Histories and request receipts must be retained in native recovery; the bounded JSON export is not a complete backup. Financial exports include both tables without internal request fingerprints, request keys or write tokens. Preserve migrated records during rollback and fence writers across migration and Worker activation.
