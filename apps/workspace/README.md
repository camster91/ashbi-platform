# Ashbi workspace — private Cloudflare pilot

This is the deployable successor to the isolated local foundation proof. It uses verified Cloudflare Access JWTs and active D1 actors; there is no fixture-code login endpoint. It does not replace the current application or migrate production records.

## Local checks

`npm ci`, `npm test`, `npm run build`, `npx playwright install chromium`, `npm run test:browser` from this directory. Build is a dry-run only. `auth.test.mjs` verifies real RSA signatures and claims; `test.mjs` runs the application handler with real local D1 through Miniflare. This is not a hosted identity/MFA login test. Tests inject a signing key into the exported handler factory; the deployed default handler always uses Cloudflare's JWKS. Fixture identities are never configured in the hosted Worker.

Scope: clients, projects, tasks, plain text project documents, one timer per staff user, manual time and bounded record export. Staff records are organization scoped; clients are limited to own, deliberately shared projects and child records. Project visibility also gates children. All mutations require the same Origin and bounded input; edits require a revision. Lists paginate at 50 records; time shows the active own timer first plus the latest 100 completed own entries (at most 101 records). No destructive delete endpoint. The UI supports create/list/edit, project and task statuses, staff assignments, calendar due dates, contact email/company, task completion and time. Notes are plain text, not a full Notion block editor.

Finance/contract signing are explicitly unavailable in the interface. The next stacked source increment adds private file upload/download, sharing and soft-removal/restoration; it is enabled only when a FILES R2 binding exists. R2 is disabled in the owning account and requires dashboard activation. No public bucket or alternative storage is substituted. Stripe credentials and webhook endpoint acceptance remain outstanding. No customers, invitations, charges or source imports are created by deployment.

The built-artifact browser suite runs `dist/worker.js` with synthetic RSA identities and actual local D1, covering create/edit/assignment/date/complete/reload/timer, local private upload/download/remove/restore, keyboard/modal focus and 390/768/1440px overflow/axe checks. A source-only browser pass initially missed Wrangler injecting `__name` helpers into a serialized function; the built-bundle check caught that failure. Client JavaScript is now a literal string, and this regression runs in CI after the build. Local browser bootstrap required an alternative Chromium binary because the standard download was truncated in this environment; that is test tooling only, never a production auth bypass.

## Data, deployment and rollback

A new D1 database is independent of the existing PostgreSQL application. Schema is additive in this new database; never replay it over existing data. No business data is seeded. Access actors are provisioned through an approved administrative operation. Runtime configuration stores only public identifiers. Tokens/secret keys do not belong here.

Deployment uses the reviewed dry-run bundle via the connected Cloudflare API. Keep workers.dev disabled until schema, actor mapping and Access policy are verified; disable version preview URLs. Production release metadata must record bundle SHA-256, source tree, Worker version and D1 ID. Enable observability at 10%, with invocation logs disabled and query strings redacted; app code never logs content or tokens. `/health` returns status and release only; Access may intercept it at the edge.

Rollback the isolated pilot by disabling its workers.dev route; preserve the D1 database and Access configuration for investigation. Do not roll back the existing Hub or restore exposed historical seed data. Export is limited to 1,000 records per table and explicitly refuses larger exports; it omits identities and does not include private objects. It is not a complete backup. No source-system deletion or cancellation is authorised by this pilot.

## Private originals (local implementation; hosted activation pending)

`files.test.mjs` uses actual local Miniflare R2 and D1. Migration `0003.sql` adds metadata only; apply it once to the isolated hosted D1 only when releasing the file increment. Before binding R2, activate it through the owning account's reviewed dashboard flow and create a private bucket with public access disabled. This repository deliberately contains no live R2 binding until that gate is satisfied. Deploying these sources without FILES leaves the feature unavailable.

Uploads are limited to 5 MiB based on bytes read, not trusted Content-Length. D1 pending metadata is reserved before an immutable random object key is written; SHA-256 is supplied to R2 and checked again on download. An interrupted upload may leave pending records/objects requiring reconciliation; they are never visible through the API. A retry after a lost response can create a duplicate. Soft removal keeps original bytes and costs storage; staff can restore using revisions. Files always download as attachments. Client upload and inline preview are outside this slice. Arbitrary attachments are not antivirus-scanned; use synthetic records during this pilot.

The record export remains unchanged and excludes file metadata/bytes. Soft restoration is not a disaster-recovery rehearsal. #282 still requires an independent backup, isolated restore, metadata/object/hash reconciliation and recovery acceptance before real customer files or source migration.

## Active timer recovery API (source increment)

`GET /api/timer/current` returns the signed-in staff member's current timer and its project name, or an explicit null when none is running. It reads one active session independently of completed-history bounds and rejects caller-selected actors and pagination parameters. Clients cannot read timers. Existing start/stop/manual contracts, the one-running-timer constraint, actor attribution and exactly-once stop behavior remain unchanged. Billing metadata/locks still need their own verified increments. No schema change or hosted action is included.

Staff now have a shared header timer and project start/stop controls, alongside the existing Time screen. They recover from persisted state on reload, route changes, window focus or explicit Refresh timer. There is no claim of continuous cross-device synchronization. Project controls disable a second start while another project is running. Manual time remains available, and the selected project/manual-minute draft survives timer operations on the Time screen; a successful manual save clears its minute input. Header/project actions preserve unsaved forms on other pages. Drafts are local to the current page visit.

Timer reads have their own request generation. A new read or timer mutation invalidates old reads, including failures and busy-state cleanup. Mutations always reload current server state, so a lost start acknowledgement still recovers its Stop control and a second stop can recover an already-completed session without rewriting it. Stable header controls preserve focus; keyboard Stop returns focus to Refresh timer only while the initiating route and focus intent are still current. Old project-action errors cannot appear on a newer page. Clients receive neither header nor project timer controls.

`browser-timer.mjs` adds two-browser recovery beyond 100 completed entries, separate signed staff/client identities, Time/manual draft retention, concurrent stops with a delayed acknowledgement, lost-start recovery, stale reads and project actions, retry, keyboard and 390/768/1440px axe/overflow checks. The first shared-control regression fails on the parent build and passes with the UI. This remains synthetic local/CI acceptance; real-user daily-use, billing attribution/locks and cutover remain separate.

## Time metadata, review and financial access (source increment)

Migration `0007.sql` adds time metadata, immutable revision events and an explicit `actor_finance_access` grant table. It grants no financial authority. Existing time IDs, actors, organization/project links, clock timestamps and seconds remain intact. Each older row gets a baseline snapshot so its first correction retains the original seconds. Historical source kind, work date, billable flag, rates, currency and metadata creation date stay unknown; baseline author and recorded date also remain unknown. Grant assignment for real people is a separate approved configuration/data action. Only an active staff actor with a grant can review money or approve/reject time; a client grant cannot authorize client access.

New manual/timer entries capture their known source and optional literal description/billable flag. New entries default billable on, matching the retained legacy contract. Manual entries accept an explicit ISO work date; otherwise new entries use the current Toronto date. Owners and financial staff can correct a pending/rejected entry's description, date, billable flag and completed recorded seconds (1–86,400). Clock timestamps remain intact, and the journal retains the original and adjusted seconds. Running seconds cannot be edited. Unknown historical dates/flags must be declared before approval.

`GET /api/time/entries` pages 50 scoped records with project, actor, review, billable, invoiced, currency and work-date filters applied before pagination. Default scope is own time; team scope and currency filtering require financial access. `/api/time/details/:id` reads or conditionally edits one permitted entry, and `/history` pages its snapshots by revision. Ordinary staff cannot read another staff member's metadata or financial fields. The existing `/api/time` active-plus-100-history response and `/api/timer/current` remain compatible and omit internal write tokens.

Approval requires a completed entry, declared date/billable status, and explicit currency/integer minor-unit hourly rate for billable work. Supported currency codes retain CAD/USD/EUR/GBP without conversion. Optional rate references are reviewer supplied; no historical rate is guessed. Approval locks edits for owners and reviewers. A financial reviewer must explicitly reject with a reason before corrections; editing rejected time resubmits it as pending while retaining the reason in history. Any existing invoice reference prevents editing or rejection for everyone. Caller-controlled source, ownership, review actor/date and invoice links are rejected. Invoice preparation/claim creation and its UI are separate increments; this API does not issue or reissue invoices.

Time creation, stopping, duration/metadata edits and review commit their affected rows and event in one D1 batch. A random write token binds capture to the successful writer, including stops sharing the same timestamp. Revision and lock predicates repeat inside the write, and financial authority is rechecked there. Snapshot/metadata failure rolls back base seconds, metadata and events together. Events capture actor, owner, project, raw clock timestamps, recorded seconds, review and price references. Read projections check effective authority in the query; ordinary staff receive no rate/currency/reference snapshots. Record exports include own nonfinancial metadata/events, or organization-wide financial data for authorized reviewers. Grants/identities remain part of the administrator backup procedure, not the application export.

## Document hierarchy, archive and search (source increment)

Migration `0006.sql` adds document positions and snapshot position metadata. Existing documents become active roots without changing their content or sharing. Parents must belong to the same organization and project. Foreign keys and atomic ancestry checks reject invalid parents and concurrent cycles. A document write, position update and version snapshot commit in one D1 batch; a failure rolls all three back. Content restoration keeps the current position and archive choice.

Clients can read or search a document only when it, every ancestor and its owning project are shared and active for their own client. An internal or archived ancestor hides descendants. Staff can include archived records, archive or restore a document, move it to another parent, and view its location. Restoring a parent preserves each descendant's own archive flag. The parent picker excludes the current document and its descendants; the server rechecks every move.

Search matches literal title/content text before pagination. Project and parent filters also apply before the stable 50-record page. Open children selects a direct parent; Root documents shows roots. Filters and paging retain an unsaved create draft during the current visit. Navigation discards that draft. Search and pagination use route-local generations so old responses, failures, busy state and focus cannot affect a newer visit. Parent choices use the existing bounded selection limit of 1,000 records.
