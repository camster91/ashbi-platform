## Authentication and recovery

`AUTH_MODE=hub` requires the canonical `APP_ORIGIN=https://hub.ashbi.ca` and the explicitly trusted `HUB_AUTH_ORGANIZATION_ID`. The Worker forwards only the host session cookie to the retained origin's `/api/auth/me` on every protected request. It refuses inactive/revoked sessions, foreign organizations, unsupported roles, incomplete MFA, support-view identities and mismatches with the active D1 actor role. Email matches only pre-provisioned workspace actors; this does not auto-create users or grant clients access.

The native sign-in page supports existing passwords, authenticator/recovery-code challenges, required enrollment, password-reset links and logout. The origin owns password policy, account/IP throttles, MFA and revocation. An exact authentication endpoint allowlist prevents this from becoming a general proxy. Mutations require same-origin JSON and the existing body bound. Only the session cookie is forwarded, with host-only Path=/, Secure, HttpOnly and SameSite=Strict. Tokens/passwords are not saved in browser storage. Authentication service failures fail closed.

Cameron and Bianca have matching active Hub accounts. Any workspace actor without an existing Hub account needs separately authorized provisioning; an email match alone does not establish a valid session. Retain the Hub origin and its account database while it provides authentication. Do not replace this route with a Worker Custom Domain: same-zone origin fetch behavior is a required architecture boundary. See [Cloudflare Routes](https://developers.cloudflare.com/workers/configuration/routing/routes/).

Access JWT authentication remains only as a backward-compatible rollback mode when `AUTH_MODE` is absent. The native-mode runtime does not accept Access assertions. Disable the obsolete workers.dev Access gate with a reversible bypass policy only after native routing, unauthorized request rejection and sign-in behavior are verified. Retain its application/audience and the private policy backup for rollback. No Access app is added to hub.ashbi.ca. Other Access applications are out of scope.

## Reviewed invoice drafts and source claims (source increment)

The invoice API prepares a reviewable draft from approved, completed, unclaimed billable time and fixed charges. Currency, tax type/rate and final due date are explicit; no historical rates or currencies are inferred. Approved time must match the selected client/project and invoice currency. Sources retain their actor, project, exact seconds, declared date, rate, approval and observed revision. Fixed charges use an integer quantity and integer unit amount. Each time line rounds half up once from seconds and hourly minor units, followed by aggregate tax rounded half up; BigInt arithmetic rejects unsafe results without floating-point conversion.

An optional deposit is a requested installment of the full total, with its own earlier due date and a balance installment. It is not a discount, a recorded payment or a second copy of the source work. The local snapshot records this intent only. Stripe documents a deposit-plus-balance payment plan, but its current API example requires a preview version; account capability, explicit activation and sandbox acceptance remain required. Routes require a currently active staff actor with an explicit financial grant:

- `GET /api/invoices/candidates?clientId=...&currency=...`: eligible time, optional project and stable ID cursor, 50 rows per page.
- `POST /api/invoices/preview`: validate the complete selection and return totals, immutable source images, installments and a content fingerprint. No write occurs.
- `POST /api/invoices`: same reviewed input plus `fingerprint` and UUID `requestId`. Persists one local draft, all time claims and both audit journals atomically. The request key is organization scoped, so either authorized staff reviewer can recover a lost acknowledgement. A different intent with the same key conflicts; existing keys replay without trying to select the now-claimed time again.
- `GET /api/invoices`: stable 50-row list with optional client, project, status and currency filters. `GET /api/invoices/:id` returns a snapshot; `/history` pages through state events.
- `POST /api/invoices/:id/void`: observed revision and required reason. Retains claims and original history.
- `GET /api/invoices/:id/release-preview`, then `POST /release`: explicitly review the current claim image/fingerprint and observed invoice revision after the retained ten-second undo window. Release is allowed only for a voided local draft with no provider reference, uncertainty or payment evidence. It clears exactly the original claims, adds RELEASE snapshots, and preserves the original invoice and prior CLAIM history. Rebilling requires a new reviewed draft.

Input shape: `clientId`, optional `projectId`, `title`, `currency`, `dueOn` (ISO calendar date), `tax: {type, rateBps}`, `times: [{id, revision}]`, `charges: [{description, quantity, unitMinor}]`, optional `deposit: {amountMinor, dueOn}`. Up to 50 time entries and 50 fixed charges fit one reviewed selection. Unsupported keys, duplicate sources, fractional money, malformed dates and overflows fail closed. No send, charge, provider ID or payment status can be supplied by these endpoints.
